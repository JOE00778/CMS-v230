## 0. 背景：这个页面到底要回答什么问题

投放广告的目的不是买曝光、点击或加购，而是**买可复制的正 ROI**——
找到一个「投 1 块赚回 ≥1 块（含利润）」的公式，然后放大它。
曝光/点击/加购只是通往订单路上的仪表读数，不是目的。

由此，看板的终极职责是回答两个问题，且**有严格先后**：

```
第一问：数据可信吗？   ← 不可信则一切判断作废，先修跟踪
第二问：花得值吗？     ← ROAS ≥ 盈亏线(=1÷毛利率) ?
```

这与 doc 13 §0 的总决策链一致。page38 目前**能回答第一问**
（tab_gap 归因差异、数据新鲜度红绿灯），
但**答不了第二问**——这正是本文要补的缺口。

三条纪律（doc 13 §0，页面设计需体现）：
**修复优先于加量**、**一次一变量**、**改动后留观察期**。
所以本页只做判定与展示，不提供任何调整入口（见 §4）。

## 1. 问题陈述

page38 当前展示 `cost_usd / impressions / clicks / ctr / cpc / conversions / conversions_value`，
但**没有回答「这笔钱赚没赚」**：ROAS、CPA 两列缺失，更没有盈亏线。
Boss 现在要靠人脑做 `conversions_value ÷ cost` 再和毛利率比——每次都得重算，且毛利率靠记忆。

判断标准本身很确定：

```
盈亏平衡 ROAS = 1 ÷ 毛利率
等价形式：CPA < 单均毛利额
```

**这件事只有 CMS 做得了**：毛利率在 `nst.sales_daily`（revenue / gross_profit），
Google Ads 后台、GA4、任何第三方广告工具都拿不到进货成本。这是 CMS 接广告数据的核心价值点，
不做这一层，page38 就只是 Ads 后台的一个只读镜像。

## 2. 架构冲突（先拍板，再动手）

page38 用 `MARKETING_DATABASE_URL`（cms_reader 角色，**仅三视图 SELECT**），
页面 docstring 明确写了「不用 shared.db 的超级用户连接」。
而毛利率在主库 `nst.sales_daily`。**两个数据源不在同一个连接里。**

三个方案，别同时写两套：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 毛利率作为**可配置参数**（page32 系统参数设定 或 page38 侧栏 number_input），人工季度更新 | 最小改动，零架构变更。毛利率本来就不是日频变化的量 |
| B | page38 额外开一条 shared.db 连接查 `nst.sales_daily` | 破坏本页「只读 marketing」的设计边界，权限面变大 |
| C | marketing schema 新增毛利视图，元川侧迁移 | 需要 003/004 迁移 + 元川部署，跨机器协调 |

**推荐 A**：毛利率一个季度动一次都算勤快，做成自动同步是过度工程。

> **2026-07-27 已核实**：自建站销售**尚未进入 NST**（该表 20 店全为平台店），
> 但 **NST 的 Shopify 接入正在进行中**（Boss 告知）。
> 因此方案 B/C 现在即使实现也取不到自建站的数——**方案 A 是当前唯一可行解**，
> 而非仅仅「更省事」。待 NST Shopify 数据就绪后再评估升 C，详见 §3.3 升级触发条件。

## 3. 需求明细

### 3.1 新增计算列（tab_camp「Google campaign 日次」表）

| 列 | 公式 | 格式 | 备注 |
|---|---|---|---|
| ROAS | `conversions_value / cost_usd` | `%.2f` + `x` | 分母为 0 时显示 `—`，不显示 `inf` |
| CPA | `cost_usd / conversions` | `$%.2f` | 转化为 0 时显示 `—` |

两列都放在 `conversions_value` 之后。`column_config` 的 `help` 写清口径来源是 Ads 归因。

### 3.2 保本线判定

页面顶部 KPI 区新增一个 metric：

- **本月 ROAS vs 保本线**：`本月ROAS` 主值，delta 显示 `保本线 X.XXx`
- 判定灯（用 `st.success` / `st.warning` / `st.error` 或彩色 caption）：
  - ROAS ≥ 保本线 × 1.2 → 🟢 盈利
  - 保本线 ≤ ROAS < 保本线 × 1.2 → 🟡 打平（边际）
  - ROAS < 保本线 → 🔴 亏损
  - 转化数 < 15/月 → ⚪ **样本不足，判定不可信**（优先于上面三档）

最后一档是硬要求。Boss 目前月转化个位数，任何 ROAS 判定都是噪音，
页面必须主动说「样本不够，别看这个数」，而不是显示一个红灯误导决策。
阈值 15 的出处见 doc 12（Google 官方 tCPA 建议门槛）。

### 3.3 毛利率参数

**默认值：`0.50`（50%）→ 保本 ROAS = 2.00x**（Boss 2026-07-27 拍板「按方案办」）

- 位置：page38 侧栏 `st.number_input`，范围 `0.0–1.0`，步进 `0.01`，显示为百分比
- 常量命名 `DEFAULT_GROSS_MARGIN = 0.50`，与 `MONTHLY_AD_BUDGET_JPY` 并列放在页首，
  旁边注明来源与日期，方便日后校准

#### 这个数怎么来的（依据，非拍脑袋）

本地快照 `data_warehouse/warehouse.db` → `nst_store_sales`（灌库时间 2026-05-05，6,099 行）实测：

| 口径 | 毛利率 |
|---|---|
| 全店合计（¥45.4M 收入） | **55.89%** |
| Shopee PH（最大店，¥18.6M） | 55.12% |
| Shopee Mall PH | 53.44% |
| Lazada PH | 58.74% |
| Smikiejapan COUPANG | 40.62% |

取 **50%** 而非实测 55.89%，两个下调理由：

1. **口径偏乐观**：该毛利率 = `gross_profit ÷ revenue`（NST 定义原价），
   **不含物流、支付手续费、广告费、平台佣金**。自建站真实毛利必然低于此数。
2. **保守方向**：宁可高估保本线（少判「盈利」），不可低估（误判亏损为盈利）。
   50% 对应保本 ROAS = 2.00x，整数好记，也贴近电商常见目标区间下沿。

#### 重要：自建站数据在 NST 侧尚未就绪（进行中）

`nst_store_sales` 的 20 个店铺**全部是平台店**（Shopee / Lazada / Coupang / Amazon / Yahoo），
**没有 Shopify 自建站**。

**Boss 2026-07-27 补充：NST 的 Shopify 接入正在进行中，尚未完成。**

所以这不是「永远取不到」，而是「现在还没有」。对当前实现的影响：

- **现阶段**：自建站毛利无法从 NST 自动取得 → 方案 A（手填参数）是**当前唯一可行解**
- **NST Shopify 上线后**：可评估升级到方案 C（marketing schema 暴露毛利视图），
  让保本线自动跟随真实毛利
- **但现在不要为此预留抽象**——不建接口、不写 adapter、不加 feature flag。
  §3.3 就是一个常量 + 一个 number_input，将来换数据源时改这一处即可，成本极低。

**升级触发条件（写在代码注释里，别忘了）**：
当 `nst.sales_daily`（或后继表）出现 Shopify 自建站的 `shop` 记录时，
重新评估 §2 方案 C。在那之前，这个常量就是事实源。

#### 数据局限（必须知道）

- 快照日期 **2026-05-05**，非实时；Mac 本地无 `DATABASE_URL`，默认连 SQLite

- **校准动作**：Boss 在 page37 利润分析看一眼自建站/整体实际毛利，
  或 CMS 会话在能连 PG 的环境跑一次 `nst.sales_daily` 聚合，然后改这个默认值

#### 页面必须显示的话

### 3.5 趋势曲线（Boss 2026-07-27 追加）

#### 设计要点：粒度 × 指标，不是四条并列需求

Boss 原话「日曲线、周曲线、月曲线、ROAS 曲线」——前三个是**时间粒度**，第四个是**指标**。
两者正交，不要写成四个 tab 四套代码。正确结构：

```
粒度选择器（st.radio 横向：日 / 周 / 月）   ← 同一份日粒度数据的三种重采样
        ×
指标曲线（消耗 / ROAS / CPA / 转化 / 点击 / CTR）
```

一套聚合函数 + 一个 selectbox，全部曲线共用。新增粒度或指标都只加一行。

#### 图表库

用 **altair**（`import altair as alt`），跟随 page 04/30/34 的既有写法。
不用 plotly——page 06/20 用 plotly 是历史遗留，本页属数据看板类，与 04/30/34 同族。

#### 聚合口径（关键陷阱）

**比率类指标必须先聚合分子分母再相除，不能对日值取平均。**

```python
# ✅ 正确
weekly_roas = grp["conversions_value"].sum() / grp["cost_usd"].sum()

# ❌ 错误——数学上就不对，低消耗日会被赋予同等权重
weekly_roas = grp["daily_roas"].mean()
```

同样适用于 CPA、CTR、CPC。**这条写错了整条曲线都是错的，且不会报错**，
review 时重点看这里。金额类（cost / conversions_value）才是直接 `sum()`。

#### 粒度定义

| 粒度 | 重采样 | 默认窗口 |
|---|---|---|
| 日 | 原始 `report_date` | 近 30 日 |
| 周 | ISO 周一起算（`report_date.dt.to_period("W-SUN")`） | 近 12 周 |
| 月 | 自然月（`.dt.to_period("M")`） | 近 12 月 |

> ⚠️ **实现时踩到的坑（2026-07-27 已修）**：pandas 的 `W-X` 中 X 是周**结束**日，
> 所以 ISO 周（周一起算）必须写 `W-SUN`。最初写成 `W-MON` 会把周一切到上一周——
> 2026-07-06（周一）被归入 6/30 那周。自检 assert 抓到了它。
> `tests/test_ads_roi.py::test_same_iso_week_groups_together` 锁住这个行为。

**未完整结束的当期（本周/本月）要么排除，要么明确标注「进行中」**——
否则最后一个点永远向下掉，看起来像断崖式下滑，实际只是还没过完。
这是趋势图最常见的误读来源。

#### ROAS 曲线专属

1. **保本线画成横向参考线**（altair `mark_rule` + `strokeDash`），
   让「在线上还是线下」一眼可见，不用读数字。线的值来自 §3.3 的毛利率参数。
2. **样本不足的点要视觉降级**：该期转化数 < 15 的点用浅色/虚线或加 `⚪` 标记，
   与 §3.2 判定灯同一套逻辑。不要让噪音点和可信点长得一样。
3. Y 轴不要强制从 0 开始截断异常值——ROAS 偶发高点是真实信息。

#### 现实约束（务必先告知 Boss，别做完才发现）

marketing 数据 **2026-07 才开始采集**。所以上线当天：

- **日曲线**：可用（有 ~30 个点）
- **周曲线**：约 4 个点，勉强看趋势
- **月曲线**：**只有 1 个点**，画出来是个孤点，没有任何趋势含义
- **ROAS 曲线**：在转化跟踪修复前**恒为 0**（Ads 转化 = 0），是一条贴着 X 轴的直线

结构先搭好没问题，数据攒够自然有用。但**页面要显式提示数据起始日期**，
在点数 < 3 时给出「数据积累中，趋势判读需 N 期以上」的 caption，
而不是画一条误导性的曲线。

## 5. 验收

1. `MARKETING_DATABASE_URL` 未配置时，页面行为与改动前一致（显式提示，不裸抛）
2. 转化数为 0 的日期，ROAS/CPA 列显示 `—` 而非 `inf` / `NaN`
3. 月转化 < 15 时，判定灯显示「样本不足」而非盈亏结论
4. 毛利率参数改动后，保本线与判定灯同步刷新
5. **曲线聚合正确性**：构造一组「高消耗低 ROAS 日 + 低消耗高 ROAS 日」样本，
   验证周聚合 ROAS = `Σvalue ÷ Σcost` 而非日 ROAS 均值。
   这是 §3.5 唯一会静默出错的地方，**必须有一个 assert 覆盖**
6. 粒度切换（日/周/月）后曲线与表格数据一致，不出现 `NaN` 断点
7. 当期（本周/本月）未结束时，末点被排除或标注「进行中」
8. `uv run pytest` 全绿（现基线 117 passed）
9. 上线前按 `feedback_cms_sqlite_pg_parity`：PG 上 smoke 一次主查询，别只信 SQLite 绿
