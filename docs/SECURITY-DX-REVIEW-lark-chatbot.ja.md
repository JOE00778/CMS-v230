# Lark ボット対話型 CMS データ照会 — データセキュリティ評価（DX部 審査版）

> バージョン：2026-06-06 v1 · **提案段階（未実装）**
> 対象読者：DX部、情報セキュリティ責任者、輸出事業統括、財務責任者
> スコープ：**Lark ボットが Lark の個別チャット / グループから、社内 PG のデータ（商品 / 在庫 / 発注）を対話形式で照会し応答する機能**
> 前提：本機能は **CMS ログイン門禁（別途実装中、`shared/auth.py` + Lark OAuth）とは独立**。門禁を先行リリース後、本機能は DX 審査通過を経て別 ticket で実装。
> セキュリティ視点：**外部攻撃面（公網経由）＋ データ第三者残留（Lark への出力）を同等比重で網羅**
> 姉妹文書：[SECURITY-DX-REVIEW.ja.md](SECURITY-DX-REVIEW.ja.md)（NST API データフロー審査・C0-C3 分類・RBAC の親文書）

---

## 1. 背景と要件

JO（経営者）の要望：**Lark の個別チャット / グループで、CMS 内のデータを対話形式で照会したい**。

- 照会対象：① **商品情報** ② **在庫** ③ **発注**
- データソース = 生産 PG（経営の単一事実源、`nst.*` を含む）
- **セキュリティ懸念（JO が明示）**：
  - ① 応答経路が **公網を経由**する（Lark → 自社サーバー）
  - ② 経営データが **Lark チャット履歴に残留**する（larksuite クラウド、スクショ / 転送可能）

本書はこの 2 点を中心に、DX が「実装可否」と「実装条件」を判定できる材料を提供する。

---

## 2. アーキテクチャとデータフロー

### 2.1 データフロー

```
ユーザー（Lark で質問：「4901301447647 の在庫は？」）
   │
   ▼  Lark 開放プラットフォーム
   │  im.message.receive_v1 イベント（署名付き、Encrypt Key で本文暗号化可）
   ▼
╔═══════ 信頼境界（社内）═══════╗
   │  Cloudflare Tunnel 経由（公網ポート 0 露出）
   ▼
コールバックエンドポイント /lark/event
   │  ① Lark 署名検証（非 Lark 由来は即拒否）
   │  ② 送信者認可（union_id ホワイトリスト照合）
   │  ③ 固定テンプレートで PG 照会（parameterized query）
   │  ④ ロール別フィールド整形（一般には原価非返却）
   ▼
   │  Lark API でメッセージ返信
   ▼
ユーザーが Lark 上で結果を閲覧（← データ残留点）
```

### 2.2 推奨実装

**cms_api（FastAPI）に `/lark/event` エンドポイントを追加**。理由：

- CMS の PG 接続・デプロイ・Cloudflare Tunnel を**再利用**（新規インフラ・新規公網ポート不要）
- セキュリティ制御（署名検証・ホワイトリスト・フィールド制限・監査ログ）が**コードで可監査**
- 代替案 N8N（既存の Lark 加签 + PG 接続あり）は導入が速いが、低コードフロー内の制御が監査しづらく、本件の機密度（C3 含む）には cms_api 案を推奨

## 3. 公網露出面の評価

新規の公網入口は **イベントコールバックエンドポイント 1 つのみ**。

| 制御 | 内容 |
|---|---|
| **Cloudflare Tunnel 経由** | CMS `smikie-cms.cc` と同方式、**実ポートを一切開かない**（公網ポート 0 露出）。コールバック URL = `https://<sub>.smikie-cms.cc/lark/event` |
| **Lark イベント署名検証（必須）** | Verification Token + リクエスト署名を検証。**Lark 由来でないリクエストは即 401**。これが「公網に開いても外部から叩けない」根拠 |
| **Encrypt Key 暗号化** | Lark → サーバー間でイベント本文を暗号化（推奨設定） |
| **送信元 IP 制限（補助）** | Lark 公式 IP レンジのみ許可、レート制限 |

**結論**：露出面は既存 CMS サイトを超えない。新たな実ポートは開かず、署名検証で外部からの実質的な到達を遮断する。

## 4. データ資産分類（親文書 C0-C3 を踏襲）

[SECURITY-DX-REVIEW.ja.md 第 5 章](SECURITY-DX-REVIEW.ja.md) の C0-C3 分類を本機能の照会対象に適用：

| 照会対象 | フィールド例 | 分類 |
|---|---|---|
| 商品情報 | 品名・JAN・規格・メーカー | **C1**（社内） |
| 在庫 | 在庫数量 | C1 ／ 在庫月数 = **C2** |
| 発注 | サプライヤー・発注数量 | **C2** ／ **発注金額・原価 = C3（最高機密）** |

⚠️ **本機能で C3（原価・発注金額）を Lark に出力するか否かが、本書最大の決議点**（第 9 章 議題 1・2）。

## 5. データセキュリティ脅威マトリックス

| # | 脅威 | 説明 | 緩和策 |
|---|---|---|---|
| L1 | 公網攻撃面 | コールバックエンドポイント露出 | Tunnel 0 ポート + **署名検証必須** + Encrypt Key 暗号化 |
| L2 | 越権照会 | グループ内の無関係者・範囲外社員が経営データを取得 | 送信者 union_id を**門禁の可用範囲 / admin 名簿と突合**、範囲外は応答拒否；機密照会は個別チャット限定 |
| L3 | **データ第三者残留** | 照会結果が **Lark チャット履歴（larksuite クラウド）に残存**、スクショ / 転送 / 退職者端末に残る | **最大決議点**：出力可フィールドの限定；**C3 はマスキングまたは非返却**；明細は CMS Web（門禁付き）へ誘導；Lark 側メッセージ保持ポリシー確認 |
| L4 | インジェクション / 濫用 | 自由文 → SQL / LLM インジェクション | **任意 SQL 非開放**；固定パラメータ化テンプレートのみ；自由 LLM-to-SQL は不採用 |
| L5 | 認証情報漏洩 | `LARK_APP_SECRET` / PG 接続文字列 / Encrypt Key | env 注入、コード / chat 非格納、CMS と同管理、ローテーション SOP |
| L6 | 監査欠如 | 誰が何を照会したか不明 | **照会監査ログ**（送信者・時刻・コマンド・対象）、append-only、保持 ≥ 2 年 |
| L7 | なりすまし応答 | 偽イベントでボットに誤応答させる | L1 の署名検証で遮断（同一根拠） |

## 6. アクセス制御設計

- **送信者認可**：イベントの `sender.open_id` / `union_id` を、CMS 門禁の**可用範囲（Lark アプリ「利用可能範囲」）**と突合。範囲外は応答拒否。門禁とホワイトリストを**単一ソース化**。
- **チャネル方針**：C2 / C3 を含む照会は**個別チャット（1:1）限定**。グループでは「DM で送信しました」のみ返し、**明細をグループに出さない**（旁観者対策）。
- **ロール別フィールド**：門禁の `admin` / 一般ロールにより返却フィールドを変える。一般ロールには**原価・発注金額を返さない**（第 4 章 C3）。

---

## 7. 固定照会テンプレート（任意 SQL 非開放）

| コマンド | 入力 | 返却フィールド | 機密度 |
|---|---|---|---|
| 商品照会 | JAN / 商品名 | 品名・JAN・規格・メーカー | C1 |
| 在庫照会 | JAN / 商品名 | 在庫数量・在庫月数（倉庫別） | C1 / C2 |
| 発注照会 | サプライヤー / 月 | 発注明細（**金額は admin ロールのみ**） | C2 / C3 |

- すべて **psycopg parameterized query**。ユーザー入力を SQL に直接連結しない。
- **自然言語 → 自由 SQL は採用しない**（L4 インジェクション面を構造的に排除）。
- 専用 PG ロール **`lark_bot_reader`** を新設：指定ビューの読込専用、原テーブル / cost 列はデフォルト不可視（親文書 第 8 章「下流コンシューマ隔離」に準拠）。

---

## 8. 既存 CMS / NST セキュリティとの関係

- 本機能は PG の**下流コンシューマ**であり、[SECURITY-DX-REVIEW.ja.md 第 8 章](SECURITY-DX-REVIEW.ja.md)「下流コンシューマ隔離」と第 7 章 RBAC に従う。
- `lark_bot_reader` ロールは輸出事業ビューのみ GRANT、cost / sales 機密列はデフォルト未付与。
- 既存の Lark 連携（[lark_notify.py](../shared/lark_notify.py) = **通知のみ・送信専用**、[lark_openapi.py](../shared/lark_openapi.py) = 表書込）とは別機能。本件は**受信 → 照会 → 応答**の双方向であり、新規の制御が必要。

## 9. DX部 重点レビュー / 決議事項

| # | 議題 | 決議形式 | 視点 |
|---|---|---|---|
| 1 | **経営データ（商品/在庫/発注）が Lark チャット履歴に残留することの可否** | 経営者 + DX 承認 | 内外 |
| 2 | **C3（原価 / 発注金額）を Lark に出すか / マスキングか / 非返却か** | DX + 財務 連署 | 内部 |
| 3 | グループ照会の可否（個別チャット 1:1 限定にするか） | DX | 内部 |

| 5 | コールバックエンドポイントのアーキテクチャ（cms_api 推奨 vs N8N） | DX + 開発 | 外部 |
| 6 | Lark イベント署名検証 + Encrypt Key 暗号化の必須化 | 開発実装 | 外部 |
| 7 | 専用 PG ロール `lark_bot_reader`（ビュー限定）の設計 | T-ticket | 内部 |
| 8 | 照会監査ログ（送信者 / 時刻 / コマンド / 対象）と保持期間 | DX | 内外 |
| 9 | 固定テンプレート方式（自由 SQL 非開放）の承認 | DX | 外部 |
